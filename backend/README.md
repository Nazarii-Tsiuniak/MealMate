# MealMate Backend — етап 3, лабораторна №8–10

Окремий Python-сервер. Flutter тепер підключено до API на етапі 4; [запуск Android та перевірки інтеграції](../SERVER_INTEGRATION.md). Демонстраційний REST-модуль лишається окремим.

## Реалізовано

- FastAPI → Router → Service → Repository → SQLAlchemy → SQLite.
- Реєстрація, вхід із JWT Bearer, отримання та оновлення власного профілю.
- Argon2id через pwdlib; зберігається лише хеш пароля.
- Email перевіряється email-validator, нормалізується й є унікальним без урахування регістру.
- Пароль реєстрації: 8–128 символів, не лише пробіли; пробіли в паролі не обрізаються.
- JWT HS256 із перевіркою підпису, дозволеного алгоритму, exp, iat, sub, issuer та audience. За замовчуванням діє 30 хвилин; суб’єкт — UUID користувача. Після видалення користувача токен не дає доступу.
- Денна ціль: ціле число 1–100000 ккал, початково 2000 як демонстраційний приклад, не персональна рекомендація.
- Сім ORM-таблиць, індекси, зовнішні ключі, CHECK та UNIQUE; початкова міграція Alembic.
- Дані зберігаються на диску після перезапуску. Таблиці створюються міграціями, а не автоматично при старті API.
- Помилки валідації не повертають початкове значення поля (зокрема пароль); помилки 500 не показують SQL, секрети чи traceback.

Додано CRUD API рецептів, план, автоматичні й ручні покупки та статистику калорій. Flutter підключено на етапі 4; інструкції — у ../SERVER_INTEGRATION.md. Початкової міграції `0001` достатньо, ORM-схема не змінювалася.

## Windows / PowerShell: перший запуск

Потрібен Python 3.11 або новіший; перевірено з Python 3.13.7. Не потрібно активувати середовище чи змінювати ExecutionPolicy.

```powershell
cd D:\IPZ-43\App\backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Для запуску без тестових залежностей можна встановити лише `requirements.txt`.

Створіть локальний `.env` із випадковим ключем. Команда **не друкує ключ** та відмовиться перезаписувати вже наявний файл:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; from pathlib import Path; Path('.env').open('x', encoding='utf-8').write('MEALMATE_JWT_SECRET=' + secrets.token_hex(32) + '\nMEALMATE_DATABASE_URL=sqlite:///./data/mealmate.db\nMEALMATE_ACCESS_TOKEN_MINUTES=30\n')"
```

Альтернатива — заповнити `.env` за зразком `.env.example`. Секрет має містити щонайменше 32 байти; не використовуйте приклади або передбачувані повторення. `.env`, бази й журнали SQLite не додаються до Git. Змінні середовища мають пріоритет над `.env`.

Застосуйте міграцію й запустіть API:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000 --reload
```

- Swagger UI: http://127.0.0.1:8000/docs
- OpenAPI: http://127.0.0.1:8000/openapi.json
- SQLite: `backend/data/mealmate.db`. Відносний шлях завжди рахується від каталогу backend.
- Майбутня адреса для Android-емулятора: `http://10.0.2.2:8000`. Flutter на цьому етапі її ще не використовує.
- Сервер слухає loopback комп’ютера. HTTP тут призначено для локальної розробки.
- Для зупинки: Ctrl+C. При повторному запуску використовуйте той самий `.env` і базу; генерацію ключа повторювати не потрібно.
- Без JWT-секрету API не запускається. Міграції секрету не потребують.
- Зміна секрету робить раніше видані токени недійсними. Вихід на клієнті надалі прибиратиме токен; окремого серверного відкликання JWT на цьому етапі немає.

## Перевірка через Swagger UI

1. Відкрийте `/docs`, розгорніть `POST /api/v1/auth/register`, натисніть **Try it out** і введіть, наприклад:

```json
{
  "name": "Назарій",
  "email": "nazar@example.com",
  "password": "Laboratory-pass-123"
}
```

Це лише приклад для локального тестового облікового запису. Очікується **201**, UUID, email, ім’я та ціль 2000. Пароль/хеш у відповіді відсутні. Повторна реєстрація цього email дає **409**.

2. Виконайте `POST /api/v1/auth/login`:

```json
{"email": "nazar@example.com", "password": "Laboratory-pass-123"}
```

Очікується **200**, `access_token`, `token_type: bearer`, `expires_in: 1800`. Неправильні дані — **401**.

3. Скопіюйте лише `access_token`. Натисніть **Authorize** вгорі Swagger, вставте токен у поле HTTPBearer **без** префікса `Bearer`, підтвердьте авторизацію.
4. Виконайте `GET /api/v1/users/me`: відповідь **200** із власним профілем.
5. Виконайте `PATCH /api/v1/users/me`:

```json
{"name": "Назарій", "daily_calorie_goal": 1800}
```

Очікується **200**. Доступні лише `name`, `email`, `daily_calorie_goal`; можна передавати частину полів. Повторіть GET і перевірте 1800. Порожній PATCH дає **400**, некоректна ціль — **422**.
6. Перезапустіть сервер, повторіть GET або login: користувач та ціль залишаються.
7. У Swagger зробіть **Logout** і повторіть GET: очікується **401**. Другий користувач бачить і редагує лише власний профіль.

## HTTP-статуси

| Статус | Приклад |
|---|---|
| 200 | Вхід, профіль, списки, статистика, PUT/PATCH |
| 201 | Створено користувача, рецепт або ручний продукт |
| 204 | Ресурс видалено, тіло відповіді порожнє |
| 400 | Пошкоджений JSON або порожній PATCH |
| 401 | Немає Bearer-токена, неправильний пароль, недійсний/прострочений JWT |
| 404 | Ресурс відсутній або належить іншому користувачу |
| 409 | Конфлікт email/даних або заборонене редагування автоматичних покупок |
| 422 | Некоректні поля запиту, зайві поля, null у змінюваному полі |
| 500 | Внутрішня помилка; клієнт отримує лише загальне повідомлення |

Помилки мають `detail`: рядок або список безпечних описів помилок полів. Усі прикладні повідомлення українською.

## Модель даних

- `users`: UUID, унікальний нормалізований email, ім’я, password_hash, daily_calorie_goal, дата створення.
- `recipes`: власник, опис, категорія, час, calories (на порцію, допускає NULL), servings (вихід рецепта).
- `ingredients`: власник, назва та нормалізована назва, унікальна в межах користувача.
- `recipe_ingredients`: власник, recipe_id, ingredient_id, quantity/unit/note, порядок. Кількість додатна або NULL із note «за смаком» та без одиниці.
- `preparation_steps`: власник, рецепт, текст, унікальна позиція у рецепті.
- `meal_plans`: власник, календарна дата, breakfast/lunch/dinner, рецепт, planned_servings (початково 1). Один слот на користувача/дату/тип.
- `shopping_items`: власник, початок тижня, назва, кількість, одиниця, категорія, is_manual/is_purchased. Ключ автоматичного групування унікальний у межах користувача та тижня; ручні записи мають NULL-ключ і можуть бути окремими позиціями.

Складені зовнішні ключі забороняють прив’язати чужий рецепт/інгредієнт до запису іншого власника. `PRAGMA foreign_keys=ON` застосовується на кожному з’єднанні. Видалення рецепта каскадно прибирає його кроки, зв’язки з інгредієнтами та записи плану. Цю цілісність перевірено також через CRUD-маршрути; видалення рецепта в тій самій транзакції оновлює покупки всіх зачеплених тижнів.

Flutter-тести на цьому етапі не запускалися, оскільки Flutter-файли не змінювалися.

## Предметне API: етап 3

Усі наведені маршрути захищено JWT. Вхід через `/auth/login` і **Authorize** у Swagger залишається таким самим. Списки повертаються JSON-масивами; порожній результат — `[]`. Для невідомого або чужого UUID повертається 404; некоректний формат UUID — 422. Передавати `user_id` у тілах запитів не можна: власник визначається лише з перевіреного JWT.

| Метод | Маршрут | Призначення |
|---|---|---|
| GET | `/api/v1/recipes?search=омлет&category=breakfast` | Каталог; обидва фільтри необов’язкові й працюють разом |
| GET | `/api/v1/recipes/{id}` | Деталі з інгредієнтами та впорядкованими кроками |
| POST | `/api/v1/recipes` | Створення, 201 |
| PUT | `/api/v1/recipes/{id}` | Повна заміна даних рецепта, 200 |
| DELETE | `/api/v1/recipes/{id}` | Видалення рецепта, його кроків і планування, 204 |
| GET | `/api/v1/meal-plans?start_date=2026-12-28&end_date=2027-01-03` | План за включним діапазоном |
| PUT | `/api/v1/meal-plans` | Додавання/заміна одного слота, 200; id слота зберігається |
| DELETE | `/api/v1/meal-plans/{id}` | Прибрати страву, 204 |
| GET | `/api/v1/shopping-items?week_start=2026-12-28` | Автоматичні та ручні покупки тижня |
| POST | `/api/v1/shopping-items` | Ручний продукт, 201 |
| PATCH | `/api/v1/shopping-items/{id}` | Позначка придбання або зміна ручного продукту |
| DELETE | `/api/v1/shopping-items/{id}` | Видалити ручний продукт, 204 |
| GET | `/api/v1/statistics/daily?date=2026-12-28` | Денна статистика |
| GET | `/api/v1/statistics/weekly?start_date=2026-12-28` | Статистика й діаграма за 7 днів |

Дати — календарні `YYYY-MM-DD`, без часу. `week_start` покупок і `start_date` тижневої статистики нормалізуються до понеділка відповідного тижня, як у Flutter. Без дат GET плану повертає поточний тиждень; без `end_date` — 7 днів від `start_date`, без `start_date` — 7 днів до `end_date` включно. Без `week_start` покупки належать поточному тижню за датою сервера.

### Рецепт: POST / PUT

```json
{
  "name": "Омлет із зеленню",
  "description": "Легкий сніданок",
  "category": "breakfast",
  "preparation_minutes": 15,
  "calories": 320,
  "servings": 2,
  "ingredients": [
    {"name": "Яйця", "quantity": 4, "unit": "шт"},
    {"name": "Молоко", "quantity": 100, "unit": "мл"},
    {"name": "Сіль", "quantity": null, "unit": null, "note": "за смаком"}
  ],
  "preparation_steps": ["Збийте яйця з молоком", "Приготуйте омлет"]
}
```

Відповідь містить ті самі дані та серверний `id`. `calories` — ккал на одну порцію; `null` означає невідоме. Категорії: `breakfast`, `lunch`, `dinner`, `salad`, `dessert`. Одиниці: `г`, `кг`, `мл`, `л`, `шт`. PUT передає всю форму, включно з повними списками інгредієнтів і кроків. Порожні списки/кроки та некоректні числа відхиляються. Пошук українською нечутливий до регістру; `%` і `_` сприймаються як звичайні символи.

### План: PUT

Скопіюйте UUID рецепта у `recipe_id`:

```json
{
  "date": "2026-12-28",
  "meal_type": "breakfast",
  "recipe_id": "ВСТАВТЕ-UUID-РЕЦЕПТА",
  "planned_servings": 0.5
}
```

Типи: `breakfast`, `lunch`, `dinner`. Початкові порції — 1; підтримуються додатні дроби до 1000. При PUT передайте бажані порції явно, інакше буде 1. Повторення того самого запиту не створює другого слота чи дубльованих покупок. Одна порція рецепта із 320 ккал дає 320 ккал незалежно від виходу рецепта; 0,5 порції — 160 ккал.

### Покупки: POST / PATCH

Ручне додавання:

```json
{"week_start":"2026-12-28","ingredient_name":"Рис","quantity":1,"unit":"кг","category":"groceries"}
```

Категорії: `vegetables`, `dairy`, `meatFish`, `groceries` («Крупи»), `spices`, `other`. Для «за смаком» — `quantity: null`, `unit: null`. Ручні продукти зберігають введену одиницю.

Позначити придбаним:

```json
{"is_purchased":true}
```

Змінити ручну кількість:

```json
{"quantity":500,"unit":"г"}
```

Зміни рецепта/плану автоматично перераховують усі зачеплені тижні в тій самій транзакції. Формула: **кількість інгредієнта × planned_servings / servings**. Назви нормалізуються за регістром, пробілами й апострофами; маса та об’єм зводяться до г/мл; несумісні одиниці й «за смаком» залишаються окремими позиціями. Автоматичні кількості від 1000 г/мл показуються як кг/л.

Ручні продукти не видаляються при перерахунку. Незмінні кількості зберігають `is_purchased`; змінені скидають його. Еквівалентні 1 кг і 1000 г не скидають позначку. При одночасній зміні кількості та `is_purchased:true` пріоритет має скидання статусу — нову кількість потрібно підтвердити окремо. Для автоматичної позиції PATCH дозволяє лише `is_purchased`, DELETE заборонено з 409: джерело змінюється через рецепт/план.

Наявна схема зберігає кількість із шістьма десятковими знаками. Вхідна кількість має до 6 знаків після крапки; агрегування виконується Decimal, потім округлюється до 6 знаків у г/мл/шт. Якщо результат став би нулем через надто мале значення, запит відхиляється з 422 і вся зміна відкочується; фіктивний нуль не зберігається.

### Статистика калорій

Приклад денної відповіді з 0,5 порції омлету:

```json
{
  "date":"2026-12-28",
  "meals":{"breakfast":160,"lunch":0,"dinner":0},
  "known_calories":160,
  "total_calories":160,
  "daily_goal":2000,
  "goal_progress_percent":8,
  "progress_fraction":0.08,
  "remaining_calories":1840,
  "is_complete":true
}
```

Порожній прийом їжі — 0. Для страви без калорійності відповідне значення `meals` і `total_calories` — `null`, `is_complete:false`. `known_calories` містить суму лише відомих ккал. Відсоток, індикатор і різниця в такій відповіді стосуються лише відомих калорій — клієнт має показувати неповний підсумок.

`goal_progress_percent` може перевищувати 100; `progress_fraction` обмежено 1, як індикатор Flutter. Від’ємне `remaining_calories` означає перевищення цілі. Ціль береться з поточного профілю користувача.

Тижнева відповідь містить `start_date`, `end_date`, сім елементів `days` із денними даними, `chart` (дата, відомі ккал, повнота), `average_calories` та `is_complete`. Середнє — сума відомих калорій, поділена на **всі 7 днів**, включно з порожніми. За невідомих значень це середнє відомих калорій із `is_complete:false`.

### Наскрізна перевірка у Swagger

1. Запустіть сервер командами вище, зареєструйтесь, виконайте login та Authorize.
2. Створіть рецепт POST і збережіть його `id`. Перевірте GET каталогу/деталей і спільну дію `search` + `category`.
3. Додайте його PUT до сніданку на `2026-12-28` із `planned_servings:0.5`.
4. Відкрийте GET покупок за цим тижнем: для прикладу буде 1 яйце та 25 мл молока, сіль — за смаком.
5. Позначте автоматичний продукт придбаним; додайте ручний продукт.
6. Змініть порції на 2: кількості покупок оновляться, змінені позиції втратять позначку, ручний продукт залишиться.
7. Перевірте daily/weekly: 640 ккал за цей день, середнє 640/7, якщо решта тижня порожня. Змініть ціль через `/users/me` і перевірте індикатор/різницю.
8. Оновіть рецепт через PUT, зокрема інгредієнти й калорії. Покупки та статистика оновляться. Перевірте також `calories:null`.
9. Перезапустіть сервер із тим самим `.env`/SQLite: дані збережуться.
10. Видаліть рецепт: план очиститься, автоматичні покупки зникнуть, ручні залишаться. Інший користувач не бачить цих ресурсів; запит із чужим UUID дає 404.

### Перевірки етапу 3 та файли

Нові тести охоплюють CRUD, Unicode-пошук/фільтри, усі три прийоми їжі, дробові й некоректні порції, об’єднання одиниць, «за смаком», ручні позиції, статуси придбання, тижні на межі року, невідому калорійність, одночасні PUT одного слота, відкат при помилці синхронізації та ізоляцію користувачів.

Реальний Uvicorn-тест тепер перевіряє також збереження рецепта, плану, автоматичних і ручних покупок, позначок та статистики після перезапуску процесу.

## Демонстраційне наповнення рецептами

Після реєстрації власного тестового акаунта у Flutter:

```powershell
cd D:\IPZ-43\App\backend
.\.venv\Scripts\python.exe -m scripts.seed_recipes --user-email "your-email@example.com" --dry-run
.\.venv\Scripts\python.exe -m scripts.seed_recipes --user-email "your-email@example.com"
```

Вкажіть email саме свого наявного акаунта. Скрипт не створює користувачів, не змінює паролі/права й не наповнює інші акаунти. Працює з MEALMATE_DATABASE_URL / `.env`, тобто тією самою SQLite-базою, що й FastAPI. Не запускається автоматично разом із сервером.

Повторний запуск пропускає наявні рецепти. Стабільні UUID захищають від дублювання навіть після перейменування демонстраційного рецепта; користувацькі рецепти з таким самим нормалізованим заголовком не перезаписуються. Усі 10 страв додаються однією транзакцією через наявні Pydantic-схеми та RecipeRepository; наявні записи не редагуються.

Докладні порції, калорії й припущення: [SEED_RECIPES.md](SEED_RECIPES.md). Після наповнення поверніть Flutter із фону або перезапустіть його, щоб завантажити серверний каталог. У робочому акаунті з уже створеним «Омлетом» має бути 11 рецептів.
